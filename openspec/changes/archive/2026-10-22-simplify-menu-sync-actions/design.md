# Design

## Context

See [proposal.md](proposal.md) for the motivation and [macos-app-shell delta](specs/macos-app-shell/spec.md) for observable behavior. Today the app starts a 30-second discovery window only after `readPenData()` is called. The menu and details window expose a cleanup intent, a separate confirmation, and a generic read action. The export folder already persists through a `UserDefaults` bookmark. A deleting transfer requires export, safe transfer evidence, matching pen identity, and durable per-packet storage; a refused route falls back to an ordinary read. A deleting transfer commits each packet before acknowledging it, so its acknowledged prefix can be removed before file publication. The ordinary-read branch currently calls `requestCleanup`; automatic Sync and Delete must not use that separate-command path after fallback or export retry.

## Goals / Non-Goals

**Goals:**

- Persist mode and interval, defaulting to Delete and five minutes only when no saved preference exists.
- Start discovery without a menu click, sync on pen appearance, and repeat at the saved interval without overlapping attempts.
- Let Paused block future attempts without cancelling an active read.
- Keep the menu compact and put information in Connection Details.

**Non-Goals:**

- Change the deleting transfer, protocol evidence records, storage, export, or cleanup outcome model.
- Sync while the app is closed or silently choose among multiple pens.
- Treat the saved Delete mode as proof that deletion occurred.

## Decisions

1. Store mode and interval in app preferences, using the same `UserDefaults` boundary already used for the export-folder bookmark but separate keys. Absent keys mean Delete and five minutes. The allowed intervals are fixed at 1, 5, 15, and 30 minutes; invalid stored values fall back to five minutes. Mode changes persist immediately. A stored Delete mode authorizes each eligible automatic deleting transfer without a new confirmation click, explicitly replacing the prior per-read confirmation rule. The data-driven transfer gate remains authoritative. Alternative: keep mode only in memory or require a click on every launch; that would not honor the saved setting.

2. Add an app-owned automatic sync coordinator around the existing per-attempt controller and runner. It begins Bluetooth discovery on unpaused launch and listens for a fresh matching advertisement; it stops observation before an existing bounded selection scan and read, then resumes observation afterward. The current central scans with duplicate advertisements disabled, so a separate observation mode must enable duplicates to measure continued presence; the bounded pen-selection scan keeps its current behavior. Track one continuous pen appearance by its ephemeral CoreBluetooth identity and mark it absent after 30 seconds without a matching advertisement. This permits an immediate sync on a new appearance without repeatedly syncing a pen that stays in range. Independently schedule an opportunity at each interval measured from the previous attempt's start while the app runs and is unpaused, including when the same pen remains available. A single-flight gate suppresses overlapping reads; elapsed ticks while busy coalesce into one next eligible opportunity. Absence and failure wait for the next interval rather than spinning, while the discovery observer remains available for a genuinely new appearance. A missing pen is not treated as an error requiring user action. Alternative: repeatedly call the current read action on a short timer; that would produce unnecessary scans and possible duplicate concurrent reads.

3. Make Paused stop pending discovery and timers, while allowing an active read to finish. Selecting Delete or Retain while paused persists the new mode and schedules an immediate discovery opportunity. A mode or interval change during an active read affects only later attempts; the active read retains its captured mode. If several matching pens advertise, use the existing explicit pen-choice state instead of automatically selecting one. Automatic retries after a failed read wait until the next interval; a user can still choose a contextual retry. Alternative: cancel on pause or switch an in-flight read's mode; either could misreport the read or interrupt acknowledged packet handling.

4. Put Delete, Retain, Pause, and an interval submenu in `PenSyncMenu`, each with a checkmark for the saved selection. The menu shows one compact status line and nothing else it would have to explain: no counts, no cleanup prose, no failure text, and no export-folder command. Retain contextual pen choice, cancel, Retry Export, Connection Details, and Quit. `PenSyncView` shows the same saved settings and keeps progress, export-folder setup, results, and failures. Alternative: put timing in the details window only; that would not meet the requested menu control.

   Amended 2026-10-21: the third setting is labelled **Pause**, the action rather than the state, so the three settings read as one choice. The status line was reinstated at the owner's request after the first implementation removed it; the reversal is recorded in decision 8.

5. Preserve the existing route outcomes. With no export destination, no durable packet storage, unsupported identity, or unsafe evidence, automatic Delete performs the ordinary read and explains skipped cleanup in Connection Details. The automatic route never invokes separate-command cleanup after a read or export retry, including an ordinary fallback. A partial deleting read reports only the acknowledged prefix and any remaining uncertainty. Retry Export works from the durable library and never initiates another deleting transfer. The deleting transfer itself removes acknowledged packets; it has no follow-up command.

6. Keep the data path unchanged: portable `PenTransport` and fake transport tests still exercise the session separately from `CoreBluetoothPenTransport`; canonical page keys `(section, owner, book, page)`, SHA-256 fingerprints, SQLite commits, and deterministic JSON/SVG/Markdown atomic publication remain as designed. The existing deletion record's prepared -> requested -> confirmed phases and per-packet durability barrier remain the source of truth. Scheduling belongs in the macOS shell and adds no Apple imports to portable packages. Use an injectable clock, fake transport, and isolated defaults for deterministic Linux tests.

7. Measure the first interval from the schedule's start rather than from the first read, and remember each pen separately. With no pen in range, the interval opportunity still runs, so the read's bounded scan reports "no pen found" in Connection Details instead of the app going quiet until a pen happens to appear; the interval, not a rapid retry, paces it. Freshness is tracked per ephemeral pen identity, so two pens that advertise in the same window are one appearance rather than two alternating ones, and the table is refreshed when observation starts so a read that outlasted the freshness window does not make the pen it just read look like one that left and came back. Answering a several-pens question resumes the read that asked it under the authorization that read started with, so a directly driven read keeps its per-read confirmation and an automatic read keeps the saved mode. Alternative: measure the first interval from the first read, which would leave an absent pen unreported; or track one pen identity, which would make two pens in range start a read each time they alternate.

8. Reinstated 2026-10-21 at the owner's request: the menu carries one compact status line reading Idle, Syncing, Paused, a completed read with its elapsed time, Not Detected, or Failed. Decision 4 originally removed all menu status, and the requirement then read "status, counts, export paths, cleanup explanations, and failure details are absent from the menu". The reversal is narrow: counts, export paths, cleanup explanations, and failure detail still live only in Connection Details, and the requirement is now split into a compact-status requirement and a detail-stays-in-details requirement. Four distinctions are what keep the line honest rather than decorative. A missing pen is its own status because it is the condition the interval exists to report on, so any other failure reads Failed instead of borrowing that word. A read that reached the pen and carried no strokes still dates the line, because the sync did happen; only a pen that was never there reads Not Detected. An attempt in flight outranks the saved mode, so pausing during a read still reports that read; the mode item's checkmark is what says the schedule stopped. The line dates the last *completed read*, so a cancelled read records nothing and keeps the previous status, and an export retry records nothing either whether it succeeds or throws, because it republishes a read that already completed. The date is wall-clock rather than the schedule's injected clock, because the line reads as an elapsed time for a person. It is rendered with `Text(date, style: .relative)`, which already reads "3 minutes ago" and updates itself as time passes, so nothing is appended to it. Alternative: format the elapsed time into a string, which would go stale while the menu stays open.

## Risks / Trade-offs

- A short label can sound like a guarantee of deletion -> show the actual outcome and refusal reason in Connection Details; never report complete removal for a partial or refused route.
- Automatic Delete can remove data without a fresh click -> persist and visibly mark the mode, apply all existing evidence and durability gates on every attempt, and never infer success from the mode alone.
- Continuous discovery can consume resources or resync the same advertisement repeatedly -> use bounded scan windows, a single-flight gate, disappearance tracking, and interval pacing.
- Removing folder selection from the menu can hide setup -> keep it prominent in Connection Details and make the skipped-cleanup reason identify a missing export destination.
- Changing the action API can break headless acceptance setup or tests -> keep the headless runner's explicit options separate from saved app preferences and verify its runs do not start a background schedule.
- Two active deltas modify the cleanup presentation requirement -> apply this change's menu contract after the deleting-read change, and reconcile their modified requirement text before synchronizing specs.
- The app-level physical deleting read remains unverified -> preserve the existing hardware acceptance task and report that gate separately from build and simulated tests.

## Migration Plan

No stroke-library migration is needed. New preference keys default to Delete and five minutes only when absent; existing export-folder bookmarks remain intact. Replace the shell controls, preference store, and scheduler together, then run Linux portable and shell tests plus the full Mac build. Reverting the app code restores the prior manual interaction without changing saved strokes or pen protocol behavior.
