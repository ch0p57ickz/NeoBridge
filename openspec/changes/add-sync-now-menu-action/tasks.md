## Notes for follow-up work

- **Menu recursion crash (out of scope, tracked separately).** Opening the menu across a read change reproduced a stack overflow on this runner: `NeoBridgeMac-2026-10-21-225953.ips` in `~/Library/Logs/DiagnosticReports`, `EXC_BAD_ACCESS` / `SIGSEGV`, "Thread stack size exceeded due to excessive recursion", with the repeating cycle `MainMenuItemHost.requestUpdate(after:)` → `ViewRendererHost.updateViewGraph` → `ViewGraphRootValueUpdater.render` → `MenuBehavior.menuHostDidChangeMenuItems`. The two user reports at 22:04 and 22:25 share that exception and stack. The crash signature is unrelated to the Sync Now command itself: the menu changed availability on its own while a read was in flight. `openspec/changes/fix-open-menu-sync-crash` owns the fix, and its task 1.1 asks for these reports to be recorded.
- **The handoff race is fixed (was the only MINOR in review).** `runOpportunityRead()` used to consume the requested capture and then await `stopObservation()`; because that handoff is a suspension point, a Retry Export click could make the controller busy in the window, so the read was refused after the capture was cleared and the click did nothing. The capture is now read only once the controller can start the read, and the loop holds it across the wait. `testAnAcceptedRequestIsHeldWhenTheControllerGoesBusyDuringTheHandoff` pins it: with the guard removed the test fails (79 assertion failures), with the guard present it passes.
- **Accepted trade-off.** Between an automatic opportunity committing and the controller reporting `.scanning`, the menu can look enabled for the handoff window; the coordinator still refuses that click, so no second read is queued.
- **Boundary left as-is (INFORMATIONAL).** The hold covers a requested read only. An automatic attempt interrupted in the same handoff window is still left to the next interval, and `lastAttemptStart` has already been anchored, so the automatic read that never ran advances the schedule. That shape predates this change and is what "a missed tick coalesces into one attempt" relies on.
- **Boundary left as-is (INFORMATIONAL).** `stop()` clears a pending request and cancels the loop, but a cancellation that lands inside `runOpportunityRead()`'s `stopObservation()` await falls through to the automatic path. Pre-existing, and `stop()` has no production caller today (the app only starts the schedule).
- **Accepted trade-off (INFORMATIONAL).** `removesPacketsOnlyThroughDeletingTransfer` is `true` for `.requestedMode` whatever was captured, so a Retry Export after a Sync Now read in Retain reports "this read removes packets only through that transfer" about a read that requested no transfer. That matches the pre-existing saved-Retain behavior.
- **Not a gap.** `PenSyncView` (the details window) was deliberately left unchanged; offering Sync Now there is a possible follow-up.
