# Design

## Context

See `proposal.md` for motivation and `specs/page-export/spec.md` for the changed contract. `PenLibraryImporter` commits strokes to SQLite and retrieves every stored stroke for each page before publication. `FilePenExportPublisher` renders a complete, sorted page in three formats. `AtomicFileWriter` currently preserves every differing target, with three backup slots per file.

## Goals / Non-Goals

**Goals:**
- Classify JSON changes using page identity and the multiplicity of complete stroke records, rather than byte equality alone.
- Keep staged, verified, atomic replacement and independent per-file results.

**Non-Goals:**
- Read or merge exported JSON into SQLite, recover a lost library, or change pen deletion behavior.
- Remove backup files created by older releases or change the JSON format.

## Decisions

### Compare complete JSON records before deciding on preservation

Keep the byte-identical fast path. For changed JSON, validate the complete existing version-1 document before comparing it with the newly generated document. Validation covers format version, four-part page identity, and every field of every stroke record: origin-time reliability, reported milliseconds, and ordered points with coordinates, offsets, and pressure. Missing, unknown, or duplicate fields make validation fail, as do malformed values. Compare validated strokes as a multiset, counting duplicate records because equal stroke content can legitimately appear more than once. If the page and version match and the existing multiset is contained in the new multiset, publish without a backup. Formatting and stroke order alone do not make a conflict. Any parsing, schema, version, or identity uncertainty requires preservation.

Comparing only stroke counts or unique sets would mistake replacement or lost duplicate occurrences for page growth. Appending JSON text would also break its single-document format and deterministic ordering, so continue to render the full SQLite page and replace the target.

### Apply preservation by format

Give the file writer an explicit preservation decision for each target. JSON uses the comparison result; SVG and Markdown never request backups. Preserve the existing JSON through the current bounded, verified backup staging and rotation before atomic replacement when comparison requires it. If that preservation fails, leave the JSON target unchanged and report failure. Existing target symlinks remain refused for every format; backup-slot safety checks apply when JSON backup history is used. Keep generated bytes from SQLite authoritative even when the existing JSON differs.

### Keep publication and sync gates intact

The importer still commits SQLite rows before exporting and reports success only when all requested files succeed. Export failure retains committed data for retry. The journaled pen cleanup path remains gated by the existing complete-transfer, durable-import, publication, and physical A1 evidence rules; this change modifies only the publication decision.

## Risks / Trade-offs

- A malformed or future-version JSON might contain data that cannot be compared. Preserve its raw bytes before replacement; if preservation fails, report a file failure.
- Generated SVG or Markdown may contain user edits. Re-export replaces those edits without a backup, matching their role as projections; document this behavior clearly.
- A lost or reset SQLite library can produce a smaller JSON. The old JSON enters bounded backup history while the current target follows SQLite; the backup is not automatically reimported.
- Existing `.svg.bak*`, `.md.bak*`, and redundant `.json.bak*` files remain on disk. Avoid automatic cleanup because prior files might contain user edits or data unavailable in SQLite.

## Migration Plan

No format or database migration is needed. Update publication behavior and documentation, retain existing backup files, and verify the portable package on Linux and the full app gate on macOS. Rolling back restores the former policy of backing up every changed target without altering stored page data.
