## 2. Durable streaming import

- [x] 2.1 Keep `ImportBatchState` as publication progress and add orthogonal transfer kind, `inProgress`/`partial`/`complete` completion, and per-note/per-packet progress (`Packages/NeoCore/Sources/NeoCore/PenDomainInterfaces.swift:13-43`; `PenImportContracts.swift:164-200`); verify reopen tests represent `partial + published` without converting it to complete.
- [x] 2.2 Ship a SQLite-consistent, private pre-migration backup beside the file-backed database and an additive schema migration; verify backup failure leaves the original intact and disables deleting reads, legacy rows become `complete`, command-journal rows survive, and unknown state/completion values fail closed (`Packages/NeoStorage/Sources/NeoStorage/SQLitePenLibrary.swift:16-36,65-93,149-158,305-319`).

  Note: the upgrade verifies the file's own columns instead of trusting the version it records. A file that holds the version-1 tables with no version row — what an interrupted first open of an old build leaves, because that build wrote its tables and its version row as separate statements — and a file that records version 2 without the columns are both migrated and backed up rather than reported ready and then failing on the first batch read. The backup is taken before the first schema write, so it is the file as it was, and it is reopened read-only and its version read back before the upgrade proceeds; a version row that is not a number is refused as unreadable rather than treated as an older file. `save` writes a record's packet rows the way it writes its page rows, so a batch's `packet_count` and its rows cannot drift apart.

  Note: the backup is written `0o600`, which is stricter than the library file it copies — SQLite creates that one with the process umask — so "private" describes the backup, not an equality with the library; making the two equal is a separate decision. The copy is built under a temporary name beside the database and given `<database>.backup-v<version>` only after it verifies, so a partial or rejected copy never sits where the next open would read it: `backup(to:)` reuses a path that already exists, and an unreadable file there would fail every later backup and keep the deleting route closed for a reason unrelated to the file being migrated. A leftover at the final name is replaced once the new copy verifies, and a failure to remove a temporary is reported rather than swallowed (`DeletingTransferStorageTests.testALeftoverBackupDoesNotBlockTheNextOpen`).

- [x] 2.7 Implement fresh-read recovery as a new batch and reliable-stroke dedup for commit-before-ack and ack-before-disconnect crashes; verify Linux integration tests preserve all committed strokes, do not lose the unacknowledged remainder, and do not silently collapse ambiguous unreliable strokes (`Packages/NeoStorage/Sources/NeoStorage/SQLitePenLibrary.swift:12-15,124-132`).
- [x] 2.8 Mark the batch a deleting read opened failed when the read ends before its first durable packet, so no deleting batch is left in progress with nothing in it; verify a storage-level test for the marking and one session test per failure path — transport failure, link loss, refused response, malformed first packet, failed first commit, and cancellation at the first inbound wait — plus the integration scenario that reads the failed row back (`Packages/NeoStorage/Sources/NeoStorage/SQLitePenLibrary.swift`; `Packages/NeoProtocol/Sources/NeoProtocol/PenSession.swift`).

  Note: the failure is written where it happens, not by an open-time sweep. The session opens the batch before the first `0x23`, so everything from there to the read's return is one attempt: any throw with no durable packet marks the row `failed` with completion `partial` and then rethrows, which covers a transport failure, an inbound stream that ends, a refused or malformed response, a failed first commit, and a cancellation. The row is kept rather than deleted, because the journal and a later diagnosis need to see that a read was attempted, and `failed` is what keeps it out of publication. `SQLitePenLibrary.failDeletingRead` writes only for a deleting batch that is still `inProgress` with no packet, so an ordinary batch, a batch with a durable prefix, a finished batch, and an unknown identifier are untouched and a second call is a no-op. A later open deliberately does not sweep empty in-progress batches: a row records no owning process and SQLite holds no lock between packets, so a sweep could not tell a crashed read's empty batch apart from one that another process is running right now — the app and a directly-run `NeoBridgeMac` binary can both open the same library. A process that dies mid-read therefore leaves one inert `committed + inProgress` row with no packets: it cannot publish, because publication needs a durable packet, and it holds no page. The marking failure is reported together with the read's own reason through `PenSessionError.deletingReadNotRecorded` rather than instead of it, so a second storage fault cannot hide the first.
