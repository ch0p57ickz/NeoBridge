# Design

## Context

See `proposal.md` for motivation and trace paths. Today `PenSession.readNote` assembles all packets in memory, sends each `0xA4` immediately, and returns a complete transfer to the app, which then imports and exports it. `PenLibraryImporter` stores complete batches and journals only separate delete commands. SQLite already uses WAL with `synchronous = FULL`; exports render stored rows and atomically replace JSON, SVG, and Markdown files. The deleting option requires a new storage callback before each acknowledgement and a partial-batch representation. `OfflineTransferAssembler` is in `Packages/NeoProtocol/Sources/NeoProtocol/OfflineData.swift`.

### Verified repository contracts

- `ImportBatchState` has only `collecting -> validated -> committed -> published` or `failed`, with terminal `published` and `failed` states (`Packages/NeoCore/Sources/NeoCore/PenDomainInterfaces.swift:13-43`). `PenImportBatchRecord.isPublicationRetryable` accepts only `committed` or `published` (`Packages/NeoCore/Sources/NeoCore/PenImportContracts.swift:194-200`).
- `publish` moves `committed` to `published` on success; `retryExport` uses the same retryability check; `requestCleanup` requires `state == .published`; and the page-overlap guard treats every state except `published` as incomplete (`Packages/NeoStorage/Sources/NeoStorage/PenLibraryImporter.swift:112-133,155-175,413-415,435-467`). The SQLite batch row stores one `state` string and unknown state text currently decodes as `collecting` (`Packages/NeoStorage/Sources/NeoStorage/SQLitePenLibrary.swift:149-158,305-319`).
- The shell's pre-read statement and next-read/retry-export lines still describe removal after saving or publication, while `isCleanupAvailable` and `cleanupUnavailableReason` use the command gate (`Apps/NeoBridgeMac/Sources/NeoBridgeMacCore/PenSyncController.swift:75-82,152-158,177-190`). The retry calls `requestCleanup` after export (`PenSyncController.swift:341-376`).
- The session's 20-second default `dataPacket` timeout bounds waiting for the next frame; `readNote` currently sends an acknowledgement immediately after assembly (`Packages/NeoProtocol/Sources/NeoProtocol/PenSession.swift:185-223,635-677`). The version decoder exposes device name, firmware, protocol, and compression capability (`Packages/NeoProtocol/Sources/NeoProtocol/PenWire.swift:89-115,121-134`).
- The physical record names NWP-F151, firmware 3.00, protocol 2.23, and paired deleting/read-after transcripts (`docs/protocol-a1.md:513-528,608-629`). It explicitly leaves the internal removal trigger unsettled (`docs/protocol-a1.md:646-668`).

## Goals / Non-Goals

**Goals:** Make acknowledged deletion safe across a process crash, storage failure, link loss, export failure, and retry; preserve a compile-time separation between ordinary reads and the explicitly authorized cleanup read; show partial outcomes truthfully.

**Non-Goals:** Reopen `0x25` or `0x27`, infer the pen's internal removal trigger, add a page-scoped delete, require successful file publication before the first acknowledgement, or run another physical experiment as part of proposal authoring. No OCR, cloud sync, or concurrent multi-pen handling.

## Decisions

1. **Use one cleanup authorization policy with a record per deletion route.** The repository's cleanup gate remains data, not a Boolean: a route is unavailable until every verdict in *its own* evidence record is safe. Leave `PenDeletionEvidence.physicalTrace2026_10_20`, its four command-specific conditions, `deletionScope = unsafe`, and `CommandEvidenceRegistry` authorization for `0x25`/`0x27` intact (`Packages/NeoCore/Sources/NeoCore/PenCleanup.swift:140-169,260-282`). Add a transfer-option record with four separately cited verdicts under the same authorization policy. Authorize that route only for exact NWP-F151, firmware 3.00, protocol 2.23 with the observed uncompressed response; reject unknown or mismatched model, firmware, protocol, compression, or response shape. The physical trace establishes outcomes, not whether acknowledgement or transmission of the next packet is the internal removal trigger. The official SDK supplies `NextAndDelete = 0x01`; the trace supplies its measured A1 behavior. `AGENTS.md`'s cleanup-gate rule — a route may remove the pen's copy only while its own record's verdicts are safe, and every verdict has to come from a physical A1 trace — applies to both routes.

   | Transfer verdict | What a physical trace must establish | Recorded observation |
   | --- | --- | --- |
   | Request and response framing | Option `0x01` uses the documented `0x23` payload and yields accepted `0xA3` plus uncompressed, paced `0x24` packets. | `docs/protocol-a1.md:523-533,567-570`; paired 2026-10-21 raw transcript directories named at line 521. |
   | Acknowledgement-bounded scope | An unacknowledged packet remains, while an acknowledged packet prefix is removed without taking the sent but unacknowledged remainder. | Withheld packet 1: 13 handed over, all 18 remain. Acknowledge packet 1: inventory 18 to 5 and its 13 strokes gone (`docs/protocol-a1.md:608-629`). |
   | Response meaning | `0xA3` error `0x00` means the deleting transfer was accepted, not that removal is complete; the `0x24`/`0xA4` sequence and read-after inventory establish the outcome. | All runs received accepted `0xA3`; paired reads measured remaining inventory (`docs/protocol-a1.md:530-535,608-629`). |
   | Interrupted retention | Abandoning without an acknowledgement removes nothing for that packet, leaves the unacknowledged remainder readable, and permits a later normal read without a power cycle. | Withheld packet 1 retained all 18; withheld packet 2 retained 5; a normal read succeeded after abort (`docs/protocol-a1.md:584-586,608-633`). |

2. **Select the deleting option through a distinct cleanup-read path.** Keep `OfflineReadTransferOption` limited to non-destructive values and leave ordinary session defaults on `nextAndReserve`. Give the session a restricted authorization created only after this sync requests an export, the app captures its explicit confirmation, transfer evidence matches, and a writable durable library is available. That path may construct `0x23` with `nextAndDelete`; a generic read cannot. Retention, no requested export, no consent, unknown evidence, and unavailable storage take the non-destructive path with a clear reason. Decide the mode before the first `0x23`, never switch a running transfer to deleting after an export retry.

3. **Use a packet commit barrier.** The session validates and assembles each `0x24` packet using the existing packet parser and sequence checks, then awaits a storage callback before building or sending that packet's `0xA4`. The callback commits the packet's complete strokes, canonical page identities, batch/note identity, packet progress and end marker in one SQLite transaction under WAL `synchronous = FULL`; success means the transaction has returned after durable sync. A failure, malformed packet, gap, or unavailable database prevents that packet's acknowledgement and closes the attempt. Cancellation closes the attempt at its next inbound wait: no packet after the one in flight is requested or acknowledged, while a packet already received — or whose durable commit has already returned — may still be committed and acknowledged, because acknowledging it only discards a copy the library already holds. The end packet uses the same barrier before Stop. The durable record means the packet is eligible for acknowledgement; it does not assert that an acknowledgement reached the pen or that the pen removed data. This avoids a second transaction being required before acknowledgement and therefore avoids a commit/progress split window. `PenTransport` remains platform-neutral and the CoreBluetooth adapter only carries frames; no Apple framework enters a portable package.

4. **Represent completion independently of publication.** Keep `ImportBatchState` as the existing publication lifecycle; a deleting batch reaches `committed` on its first durable packet and may reach `published` after exporting its current committed pages even while incomplete. Add a durable completion field (`inProgress`, `partial`, `complete`) and per-note/per-packet progress. Mark `complete` only after every discovered note's end packet was durably committed and Stop sent; interruption leaves `partial`. Existing ordinary batches migrate as `complete`. `isPublicationRetryable` remains true for a deleting batch in `committed` or `published` when it has durable packet rows, regardless of completion. `publish`/`retryExport` render only committed pages and mark `published` only when every requested file succeeds; publication does not change completion. A fresh read creates a new batch for the remainder and may republish merged library pages; a previously published partial batch remains partial. A read that ends before its first durable packet has no prefix to publish and no completion to claim, so the session marks the batch it opened failed at the point of failure; the row is kept rather than removed, because the journal and a later diagnosis need it, and no open-time sweep reinterprets it (see Risks). `requestCleanup` refuses every deleting-transfer batch, including `published + complete`; for ordinary command deletion it still requires `published + complete` and the separate command gate. The overlap guard treats any batch with completion other than `complete` as incomplete even when publication is `published`; it also retains the existing block for unpublished batches. These decisions answer the current predicates cited in Context without widening `0x25` or `0x27`.

   A crash after the packet transaction but before its acknowledgement leaves a durable but possibly still-on-pen packet. A crash after acknowledgement leaves the same durable record and an uncertain pen inventory. Both recover through a fresh read, not a repeated delete command or a claim that the pen retained every stroke. Replay-safe SHA-256 fingerprints deduplicate reliable strokes across fresh reads. Preserve the existing rule for strokes without trusted pen time: do not collapse merely matching content across sources; where packet replay identity is ambiguous, retain data and report the uncertainty instead of dropping a stroke. The old `prepared -> requested -> confirmed` journal remains only for separately scoped deletion commands; transfer progress must not be written into that journal as a false confirmation.

5. **Require an export request, then export from the durable library.** The deleting option is available only when this sync requests an export. The pen's copy leaves as the read progresses, so the durable library plus the requested export is the user's path back to files; a no-export read has no file-publication intent and follows the existing ordinary retention rule. Export committed pages after a transfer completes, or offer publication of a partial batch after interruption. Render deterministic JSON/SVG/Markdown content from stored rows, use atomic sibling-temp replacements, and record each file's outcome. Export failure does not undo already acknowledged removal, so the UI states that the library holds the re-exportable copy and offers retry. Existing complete-batch import and export APIs remain available for retention reads; the deleting read uses streaming storage and finalization rather than feeding a second complete transfer to `importRead`.

6. **Keep consent and reporting tied to the attempt.** The shell's `nextReadCleanupMode` remains a per-sync default intent. Before opening a deleting transfer, require an explicit confirmation that says: “As this read progresses, each packet saved to the local library is removed from the pen when acknowledged. The files requested for this read are exported afterward; if that export fails, retry it from the local library.” Show Keep on pen alongside it. Capture the confirmed mode with the attempt, and reset it for the next sync. Cancellation stops the transfer at its next inbound wait: no packet after the one in flight is requested or acknowledged, and a packet whose durable commit has already returned may still be acknowledged, because acknowledging it only discards a copy the library holds. The session reports the durable prefix as a partial stop; cancelling does not show that report, because it returns the shell to idle, and the committed packets stay in the library as a partial batch that a fresh read completes. Replace the current `cleanupIntentStatement`, busy and next-read `cleanupIntentLine`, and retry-export line (`PenSyncController.swift:75-82,177-190`): retrying files for a deleting batch never initiates a new deletion. Derive `isCleanupAvailable` and `cleanupUnavailableReason` for a prospective deleting read from a requested export, the transfer record, and writable packet storage; per-sync confirmation is the final authorization before `0x01`. If no export was requested, show that specific reason and start an ordinary non-destructive read. Preserve `PenCleanupPolicy.deletionEnabled` and `skipReason` only for separate command deletion (`PenSyncController.swift:152-158`; `Packages/NeoCore/Sources/NeoCore/PenCleanup.swift:260-282`). Do not call `requestCleanup` from a deleting batch's export retry (`PenSyncController.swift:341-376`). On partial failure show the durable packet prefix, an uncertain pen copy for the last attempted acknowledgement, and a fresh-read/re-export path. Do not describe a partial batch as a complete saved sync or as confirmed whole-note removal.

## Risks / Trade-offs

- [Storage commit per packet is slower] → Measure commit latency and pen response tolerance. Task 2.6 measured the host side — the worst of five commits for a 13-stroke packet was 1.11 ms, against the 20-second `dataPacket` wait — and the pen's own tolerance is the part task 4.4 records; it stays an open gap, not a gate on the route. The current 20-second `dataPacket` deadline covers waiting for a frame after acknowledgement, not the time spent committing a received packet (`Packages/NeoProtocol/Sources/NeoProtocol/PenSession.swift:191-223,640-673`). If the pen abandons the transfer before the host acknowledges, preserve the committed packet as partial/uncertain and retry by fresh read; never acknowledge early to improve speed.
- [The app's own deleting read has never run against a pen] → The 2026-10-21 evidence comes from the PenLab driver, which frames the option itself, and the portable tests exercise the app's session and shell against fake transports. No run has yet driven the app's end-to-end deleting read against a physical A1, so the packet-commit timing, the app's own `0x23` request, the consent wording, and the paired read-after behavior are verified in isolation rather than together. Task 4.4 is the run that closes this gap; until it runs, the route is enabled on the strength of the trace and the portable tests, and the gap is recorded here rather than treated as a release gate.
- [A response shape or firmware differs] → Fail closed to an ordinary non-destructive read; do not extend the evidence record by assumption.
- [Commit and acknowledgement are separated by a crash] → Treat pen removal as uncertain; the durable copy exists, and a fresh read reconciles the remainder with replay deduplication.
- [A partial batch has exported files but is later retried] → Use current atomic publication and per-file outcomes; a retry renders the merged library state and never claims a failed file was published.
- [A pen can receive an acknowledgement whose transport send later fails locally] → Never claim exact inventory from send success or failure; report the acknowledged prefix as an evidence-bounded expectation and reconcile on fresh read.
- [A deleting read that dies before its first packet leaves an empty batch] → The session marks the batch it opened failed when the read ends without a durable packet, so the row is visible as failed and unpublishable instead of claiming an in-progress transfer for ever. The failure is written where it happens rather than by an open-time sweep: a batch row records no owning process and SQLite holds no lock between packets, so an open-time rule could not tell a crashed read's empty batch from one a second process is running right now — the app and a directly-run `NeoBridgeMac` binary can both open the same library. A process that dies mid-read therefore still leaves one `committed + inProgress` row with no packets; it can never publish and it holds no page, so the residue is inert, and a later read of the same pen starts its own batch.

## Migration Plan

Ship a pre-migration backup step for an existing file-backed library. Create a SQLite-consistent backup in the app's library directory, beside the database, under a versioned name, written `0o600` — stricter than the library file it copies, which SQLite creates with the process umask; it is not an export and not a test-only artifact. The copy is built under a temporary name and given its final name only after it has been reopened and read back, so a partial or rejected copy never blocks a later open. If backup creation or verification fails, leave the original database untouched, abort migration, disable deleting reads, and report the storage error. In-memory test libraries need no backup. Then add an additive SQLite migration for completion and packet progress, defaulting legacy rows to `complete`. Existing `collecting`, `validated`, `committed`, `published`, and `failed` publication states keep their meaning, and command-journal rows remain untouched. `SQLitePenLibrary` already rejects a newer schema version but currently maps unknown batch state text to `collecting` (`Packages/NeoStorage/Sources/NeoStorage/SQLitePenLibrary.swift:16-36,65-93,305-319`); the new build must reject unknown completion/state values rather than silently reinterpret them. Gate option `0x01` until migration is complete and transfer evidence matches the connected pen. Build and verify a rollback configuration of the new schema-aware app with deleting reads disabled; an older binary must not open the migrated database for writing. Rollback preserves stored strokes and progress for export. Run portable migration/reopen and backup-failure tests on Linux, then the full Xcode build and physical A1 acceptance on the Mac runner. The recorded 2026-10-21 trace satisfies the M0 protocol evidence prerequisite for this option, so the deleting route is enabled for the traced identity as soon as this change ships: it is reachable with a requested export, a per-sync confirmation, a safe verdict for every transfer criterion, and available durable storage. The Xcode gate (task 4.3) and the physical A1 acceptance run (task 4.4) verify the enabled route rather than gate it, and an observed mismatch closes the transfer record instead of extending it by assumption.
